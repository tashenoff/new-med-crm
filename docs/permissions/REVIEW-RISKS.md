# Границы результата и риски перед внедрением

Локальная правка готовится к review. Она закрывает воспроизведённый сценарий **сотрудник marketer с явными CRM-only правами → HMS через обычный JWT/UI/API**. Это не означает завершение всех работ по безопасности или готовность к автоматическому deployment. Live права, роли, MCP grants, конфигурация, секреты и данные не менялись.

## Что закрыто в продолжении аудита

- Кнопки CRM, задач, источников/DID, склада, справочников, сотрудников, врачей, рассылок и финансовых демоэкранов сверяют отдельные view/edit/delete/export keys. Drag/drop и отправка сообщения по Enter дополнительно проверяют права в обработчике. Сохранение формы не обходится клавишей Enter.
- В карточке пациента и записи ограничены сохранение, клиническое создание/удаление, загрузка/скачивание документов, оплата и отметка выполнения процедуры. Текущий пользователь передаётся в модальные окна из App через ModalManager; сохранённый снимок props не заменяет обновлённые права сессии.
- Скачивание зарегистрированного документа выполняется через собственный API с Authorization и blob. Исторический публичный `/uploads` не возвращён. Для patient account добавлена проверка принадлежности документа.
- `backend/api_permissions.py::check_financial_side_effects` запрещает календарному редактору создавать/изменять/удалять источник депозита без finance view/edit и patients view/edit (распределение депозита может автоматически завершать процедуры); неизменённый депозит может пройти повторное сохранение. Изменение финансового состояния legacy плана через общий PUT также требует finance view/edit. Платёж плана `full_payment_v1`, автоматически отмечающий процедуры, дополнительно требует patients_edit. Арифметика ledger не менялась.
- `tests/finance_readonly/test_permission_compatibility.py` воспроизводит совместимость MCP только на объектах в памяти. Production resolver, scopes, bindings, grants и MCP маршруты не изменены.

## Классификация

Приоритет P1 означает существенную границу доступа/целостности, P2 — несовместимость или вводящий в заблуждение интерфейс. Это оценка кода и синтетических сценариев; наличие конкретного production grant, смешанной БД или опубликованных URL не проверялось.

## Внедрение только после review

1. Независимо интегрировать backend ветку в актуальный ref-2 и frontend ветку в актуальный main. Сохранить опубликованные funnel/source/DID commits. Есть пересечения с consent в `PatientModal.js` (передача user, документные ссылки и клинические кнопки); не затереть refresh/spacing/PatientTermsStatus из соседней работы. Общие auth/server/routers требуют отдельного просмотра diff.
2. Определить применимость условных рисков выше. Не объявлять MCP/общую БД/публичные интеграции проверенными по одному JWT тесту. Если канал нельзя согласовать к выпуску, исключить его из заявленной области и удержать связанный rollout.
3. Staging с синтетическими пациентами: роли, explicit empty/omitted, round-trip, deny API/URL, revoke+focus/60s refresh, login/password-expiry recovery, зарплата, документы, депозиты, назначения и исходящий звонок. Проверить производительность clinic preflight.
4. Составить **план**, backup и dry-run изменения старых legacy сотрудников. Код намеренно сохраняет legacy поведение до явного сохранения ограниченного набора; существующий живой маркетолог автоматически не исправлен. Не выполнять массовую миграцию в этой работе.
5. Только отдельное явное поручение разрешит публикацию/деплой/миграцию. Rollback старым backend небезопасен для explicit аккаунтов: он снова объединит роль с custom_permissions; нужен rollback с сохранением новой семантики.
