# Анализ ТЗ заказчика «Комплексные услуги» — ядро пакета и общие модули

Цель: отделить функционал, который реально относится к модулю «пакет услуг», от общего
функционала CRM/МИС, который у MedCRM уже есть или является отдельной подсистемой.

Легенда:
- **ПАКЕТ** — требуется именно понятием «комплекс = набор компонентов с общей ценой/скидкой».
- **ОБЩЕЕ** — общий модуль CRM/МИС, не зависит от наличия пакетов; часто уже есть в MedCRM.
- **УЖЕ ЕСТЬ** — в текущей архитектуре MedCRM уже реализовано (проверено по коду).

---

## 1. Назначение и ключевой результат

| Пункт ТЗ | Что это | Комментарий / статус в MedCRM |
|---|---|---|
| Комплекс отображается одной строкой в прайсе, внутри — набор компонентов | ПАКЕТ | Ядро. Нужна модель комплекс/компонент |
| Единая сумма к оплате у пациента | ПАКЕТ | Следствие пакета |
| Врачу — состав, назначение, отметка выполнения без финансов | ПАКЕТ + права | Состав и выполнение — пакет; скрытие финансов — роли (ОБЩЕЕ) |
| Пациенту — чек с названием и суммой, иногда расшифровка состава | ПАКЕТ | Печать/отображение состава |
| Бухгалтерия — распределение выручки по каждому компоненту | ПАКЕТ | Распределение цены — ядро |
| Руководитель — отчёты по продажам/исполнению/марже | ПАКЕТ + ОБЩЕЕ | Отчёты про пакет, маржа — аналитика |

## 2. Термины

| Пункт ТЗ | Что это | Комментарий |
|---|---|---|
| Комплекс, компонент, базовая сумма, цена, распределённая цена, экземпляр, исполнитель | ПАКЕТ | Все термины — суть пакета. Ключевое ядро модуля. |

## 3. Роли и права

| Пункт ТЗ | Что это | Статус в MedCRM |
|---|---|---|
| Разграничение ролей (руководитель, бухгалтер, администратор, врач, кассир) | ОБЩЕЕ | Уже есть `UserRole`, `require_role`, `зависимости` |
| Аудит критичных операций | ОБЩЕЕ | Есть каталог `backend/audit` |

Вывод: роли и аудит — общий сквозной механизм, **не входит в пакет**.

## 4. Конструктор комплекса

| Пункт ТЗ | Что это | Комментарий |
|---|---|---|
| Карточка: код, название, категория, состав (активные услуги, количество, обязательность) | ПАКЕТ | Ядро конструктора |
| Цена: автоматическая от базовой суммы и скидки ИЛИ фиксированная | ПАКЕТ | Ценообразование пакета |
| Период действия, филиалы, ограничения (возраст/пол/кратность), подготовка | ОБЩЕЕ | Общие атрибуты прайса; в MedCRM у услуги есть часть (category, is_active), филиалы/ограничения — расширение |
| Статус комплекса (черновик/опубликован/приостановлен/архив) | ОБЩЕЕ (с пакетным оттенком) | Общий lifecycle прайса; «опубликован» — пакетное |
| Контрольная таблица перед публикацией (компонент, базовая цена, скидка, распределённая цена, себестоимость, правило начисления, маржа) | ПАКЕТ | Экономика пакета |
| Блокировка публикации без цены/исполнителя/правила для обязательного компонента | ПАКЕТ | Валидация пакета |

## 5. Версионность

| Пункт ТЗ | Что это | Комментарий |
|---|---|---|
| Каждое изменение — новая версия; проданные не пересчитываются | ОБЩЕЕ (принцип «заморозка цены на дату продажи») | Не специфичен для пакета — верно для любой услуги. В MedCRM нет полноценной версионности; проданный экземпляр = срез данных. Для пакета важно зафиксировать состав+цены на момент продажи (это ПАКЕТ-кусок), сам механизм версий общий |

## 6. Цена и распределение скидки

| Пункт ТЗ | Что это | Комментарий |
|---|---|---|
| Базовый алгоритм распределения (сумма базовых, коэффициент = цена/базовая, распределённая = базовая × коэффициент) | ПАКЕТ | **Ядро пакета.** Нет в MedCRM. |
| Округление до 1 тенге, остаток на самый дорогой компонент | ПАКЕТ | Детализация алгоритма |
| Фиксированное распределение (вручную внутренняя цена, сумма = цена) | ПАКЕТ | Доп. режим |
| Смешанный режим | ПАКЕТ | Этап 2 |
| Компонент без скидки, мин. внутренняя цена | ПАКЕТ | Нюансы ценообразования |

## 7. Начисление вознаграждения исполнителям

| Пункт ВТЗ | Что это | Статус в MedCRM |
|---|---|---|
| Фикс. сумма / % от распределённой цены / % от базовой / без начисления | ПАКЕТ | `salary_service` уже умеет фикс. сумму и % (от `price` в плане). Для пакет — нужно «распаковать» и подставить распределённую цену. Логика есть, привязка цены — пакет |
| Начисление только после «Выполнено» и указания исполнителя | ПАКЕТ + ОБЩЕЕ | Факт исполнения — пакет; логика «после выполнено» — общая для любой услуги |
| Доли при нескольких исполнителях | ОБЩЕЕ | Распределение между сотрудниками — общий механизм |
| Замена врача | ОБЩЕЕ | Общая логика приёма |
| Сторно при отмене, возврат после выполнения | ПАКЕТ + ОБЩЕЕ | Для пакета — по компоненту |

## 8. Продажа (отображение в прайсе + сценарий)

| Пункт ТЗ | Что это | Статус |
|---|---|---|
| Комплекс одной строкой в прайсе, раскрытие состава (нажание, не наведение) | ПАКЕТ | UI-требование пакета |
| Пациентская расшифровка (без фин-начислений/себестоимости) | ПАКЕТ + права | Пакет + роли |
| Создание экземпляра в плане лечения/заказе | ПАКЕТ | Плюс: план лечения в MedCRM уже умеет строки услуг |
| Назначение дат сразу / «требует записи» | ОБЩЕЕ + переплет | «Планирование» компонента — пакет; сам приём — существующий |
| Оплата одной суммой, внутренне распределяет выручку | ПАКЕТ | Выручка по компонентам |
| Маршрут прохождения с датами и инструкциями | ОБЩЕЕ + уведомления | Коммуникации |

## 9. Прохождение комплекса

| Пункт ТЗ | Что это | Комментарий |
|---|---|---|
| Статусы компонента (не запланирован, запланирован, подтверждён, выполнен, не явился, отменён, возвращён) | ПАКЕТ + ОБЩЕЕ | Это трекер **приёма/услуги** (в MedCRM уже есть AppointmentStatus: unconfirmed/confirmed/arrived/in_progress/completed/cancelled/no_show). Для пакета нужно перенести статус на компонент, но сами статусы общие |
| Авторасчёт статуса всего комплекса (не начат/в процессе/завершён/частично/просрочен/отменён) | ПАКЕТ | Свойство пакета — агрегируется из компонентов |
| Каждый компонент = отдельная дата/кабинет/филиал/исполнитель | ПАКЕТ + приём | Пакет требует связь приём↔компонент |
| Шкала прогресса «5 из 8» | ПАКЕТ | Агрегация пакета |
| Задачи администратору по незаписанным/пропущенным | ОБЩЕЕ | Общие задачи в CRM |
| Результаты/заключения привязанные к компоненту | ПАКЕТ + Общее | Документы у MedCRM уже есть (document), привязка к компоненту — пакет |

## 18. Критерии приемки и этапы

Критерии и этапы соответствуют ядру (конструктор, распределение, экземпляр, начисление, частичный возврат, записи на компоненты, аудит).
**Запись компонентов на разные врачи/дни/филиалы — самый трудоёмкий**, т.к. требует связи приём↔компонент. Понесён на этап МVP или отдельно.

## Итоговая сводка

**Ядро пакета — реально строить:**
1. Модель данных: Комплекс → Компоненты (состав, цены, обязательность, порядок).
2. Алгоритм распределения скидки (пропорционально/фиксированно) с округлением и контролем `∑ распределённых = цена`.
3. Экземпляр на дату продажи (состав с ценами заморожен).
4. Сумма/скидка/базовая цена по компонентам + контроль корректности.
5. Частичный возврат по распределённым ценам невыполненных.
6. Авторасчёт статуса комплекса и прогресса по компонентам.
7. Отчёты по пакетам (продажи, исполнение, обязательства, маржа, возвраты).

**Требуется в MedCRM, но это не пакет (а общее / уже есть):**
- Статусы приёма (AppointmentStatus) — уже есть, надо спроецировать на компонент.
- Запись на услугу + расписание + оценка конфликтов — уже есть (Appointment), нужен мостик приём↔компонент.
- Начисление врачу (salary_service) — % от цены уже есть; для пакета подставить распределённую цену.
- Задачи/уведомления — общий механизм в CRM.
- Отчёты (услуги — раз есть).
- Роли, аудит, права.
- Интеграции с кассой/1С/складом — вне ядра пакета (этапы 2–3).

## Риск по объёму
Самое дорогие и единственное реально «ломающее» текущую архитектуру (расписание/календарь) требование — **отдельные записи на каждый компонент пакета** (разные врачи/дни/кабинеты/филиалы). Это приводит связь приём ↔ компонент и посильное изменение модели приёма. Если заказчик согласен на MVP «пакет продаётся одной строкой, компоненты исполняются через существующие планы/записи», то ядро пакета внедряется значительно дешевле, без переделки календаря. Всё остальное из ТЗ — относительно безопасные расширения уже существующих модулей.
